## 6. Решения и целостность
Заказ с платежами, расходами, складскими операциями, отчётами или начислениями не удаляется: API возвращает 409 и предлагает отмену. Материалы/инструменты с историей либо плановыми назначениями защищены от каскадного удаления. Выданные инструменты защищены отдельно. Компании/контакты с заказами или платежами не удаляются. Аудит удаления клиентов атомарен.
При удалении последнего отчёта завершённый выезд и заказ переоткрываются. При удалении основного отчёта с оставшимися отчётами выбирается замена. Файлы удаляются через долговечную очередь; ошибки удаления сохраняются для повторной очистки. Непривязанные файлы старше суток после сбоя загрузки также подлежат очистке.

## 7. Схема и офлайн-синхронизация
Добавлена миграция `002_sync.sql`: `mutation_receipts` и `file_deletions`. В рабочую БД миграция этой сессией не применялась; миграции проверены на тестовых БД.
Для операции сохраняется уникальный ID до отправки. Изменения БД и квитанция результата фиксируются одной транзакцией; вложенные бизнес-транзакции используют savepoint. Повтор возвращает сохранённый результат. Изменённый payload под тем же ID отклоняется. Квитанции разделены по пользователям и области прав.
Версии записей вычисляются через HMAC. Устаревшие PATCH/PUT/DELETE получают 409; удалённые записи — 404. Версия проверяется внутри транзакции. Service Worker обрабатывает API только через сеть и не хранит личные API-ответы.
IndexedDB-кэш/очередь привязаны к аккаунту; смена аккаунта очищает их. Выход очищает локальные данные и блокирует автоматическое восстановление прежней cookie-сессии в интерфейсе. 401 останавливает отправку; очередь сохраняется для повторного входа того же пользователя. Смена пользователя в другой вкладке контролируется событиями storage и идентификатором пользователя в ответе API. Очередь сохраняет порядок и использует блокировку между вкладками там, где доступен Web Locks API; серверная идемпотентность действует независимо.
Лимиты: 100 операций, 40 МБ очереди, 13 МБ одной операции, 12 МБ серверной загрузки файла. Ошибки сохранения не выдаются за успех. Операции старше 30 дней отклоняются; квитанции очищаются через 45 дней. Конфликт сохраняется с сообщением и блокирует последующие операции до решения пользователем.

## Итог 18 ноября 2026: причина 1033/530 и рабочая схема

### Причина
Туннель на телефоне регистрировался на edge и через несколько секунд переставал обслуживаться: Cloudflare отвечал 1033/530, `cloudflared tunnel info` показывал «нет активных соединений» при живом процессе, а API зоны — `status=degraded` с одним соединением. Дальше edge закрывал поток (`connection with edge closed`), коннектор переподключался, и цикл повторялся.

Что исключено измерениями на самом телефоне:

| Проверка | Результат |
|---|---|
| MTU (ping с DF 1472/1400/1200) | 0% потерь |
| Скорость к Cloudflare | 5 МБ за 0,7 с (~7 МБ/с) |
| TLS 1.3 и SNI к edge:7844 (`*.cfargotunnel.com`, `region1.v2.argotunnel.com`) | хендшейк 38–79 мс |
| Долгоживущее HTTPS-соединение (60 с, запрос каждые 10 с) | 6/6 успешно |
| IPv6 | маршрута нет (`ENETUNREACH`) |
| Мобильный интернет | SIM вне сети (`OUT_OF_SERVICE`), только Wi-Fi |
| Нагрузка телефона | 3,3 ГБ свободной памяти, CPU простаивает |
| Версия cloudflared | 2026.10.3 (Android) и 2026.11.1 (linux-arm64) падают одинаково |
| Быстрый туннель (trycloudflare) | регистрация есть, публично 530 — тоже мёртв |
| Нагрузка запросами с первой секунды | 1 успех из 60, при `closes=0` |

Вывод: обычный HTTPS через тот же канал работает, а туннельный поток к `*.argotunnel.com` на прямом российском маршруте (PoP dme01/dme05/dme06) перестаёт маршрутизироваться. Это не конфигурация туннеля, не версия cloudflared и не нехватка ресурсов телефона, поэтому «починить» это на телефоне нельзя.

### Рабочая схема
- Телефон TECNO AD11: CRM `node server.ts` на `0.0.0.0:3000`, защищённая веб-консоль `ttyd` на `0.0.0.0:7681` (basic-auth, пароль в `~/pv/.console_cred`), sshd на 2222.
- ПК: планировщик запускает `deployment/termux/pv-relay.ps1`; тот держит коннектор named-туннеля `pv-main` (`778ca0e4-f20d-449d-996f-ed9fdb112912`) и проксирует запросы на телефон по домашней сети (192.168.1.112). Адрес телефона определяется автоматически, если DHCP его сменит.
- DNS: `crm` и `dev` → `778ca0e4-f20d-449d-996f-ed9fdb112912.cfargotunnel.com`, proxied.
- Результат проверки: `https://crm.gulya-studio.ru/api/health` → 200; `https://dev.gulya-studio.ru/` → 401 без пароля и 200 с паролем.

### Результаты измерений
- 4 минуты сразу после переключения: 24/24 успешных запроса.
- 10 минут: 39/40 (один 502), консоль 40/40 отвечала 401.
- 20 минут с параллельной проверкой LAN каждые 5 с: единственный обрыв длился ~50 с; LAN всё это время отвечал 200.
- Причина этого обрыва: в 17:22:29 перезапустился VPN-клиент на ПК (`sing-box`). В логе cloudflared все четыре соединения закрылись одновременно (`connection with edge closed`), затем перерегистрировались, и edge ещё ~50 с не направлял трафик. Телефон и домашняя сеть были ни при чём.
- Вывод: остаточные короткие обрывы связаны с перезапуском VPN на ПК, а не с CRM или телефоном. Полностью убрать их можно только стабильным маршрутом до edge (VPS или другой VPN).

### Автозапуск
- Телефон: `~/.termux/boot/start-pv` (Termux:Boot уже установлен) вызывает `~/pv/launch-stack.sh`; супервизор `~/pv/stack.sh` держит CRM и консоль, перезапускает их при падении и после трёх неудачных health-проверок.
- ПК: задача планировщика `PV-Relay` при входе пользователя; логи `%LOCALAPPDATA%\pv-relay\relay.log`, наблюдение за публичным health с перезапуском коннектора после 90 с недоступности.
- Проверка перезагрузкой: стек поднял релей через ADB за ~30 с, публичный адрес вернулся через 52 с, коннектор перезапускать не пришлось. Termux:Boot на этой прошивке не срабатывает: broadcast остаётся в состоянии `PENDING OFFLOAD`, затем вендорная система `Hiber` замораживает `com.termux.boot`. Поэтому автозапуск фактически обеспечивает ПК, а телефон должен быть подключён к нему по USB.

### Ограничения
- Работоспособность публичного адреса теперь зависит от включённого ПК с рабочим маршрутом. Если ПК выключен или его VPN-маршрут сломан, будет 530/1033. Перезапуск VPN-клиента на ПК даёт обрыв примерно на минуту, пока edge не начнёт снова направлять трафик.
- После перезагрузки телефона стек поднимается только при подключённом USB (релей стартует его через ADB). Без USB нужно один раз открыть Termux и выполнить `bash ~/pv/launch-stack.sh`.
- Внутри домашней сети CRM и консоль доступны по обычному HTTP; TLS терминируется на edge. Сегмент сети должен быть доверенным, порт 7681 нельзя выставлять в интернет напрямую.
- В коммите `2483c64` в отчёте остались два значения API-токенов Cloudflare. Репозиторий приватный, но токены надо отозвать в панели Cloudflare; историю не переписывали (force push запрещён).
- Не проверены: перезагрузка ПК, нагрузка 15/30 работников, тепловой режим, длительная работа без перезапуска.
