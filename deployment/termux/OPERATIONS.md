# Termux: запуск и проверка

## Текущая схема (обновлено 18.11.2026)

Схема разделена на две части, потому что прямой маршрут телефона к Cloudflare edge не держит туннельный поток (подробности и измерения — в `GOOGLE_UPDATES_MERGE_REPORT.md`, раздел «Итог 18 ноября 2026»).

| Что | Где | Адрес |
|---|---|---|
| CRM (Node) | телефон, Termux | `0.0.0.0:3000` |
| Веб-консоль (ttyd, basic-auth) | телефон, Termux | `0.0.0.0:7681` |
| SSH | телефон, Termux | `:2222` |
| Коннектор Cloudflare Tunnel `pv-main` | ПК, планировщик `PV-Relay` | `deployment/termux/pv-relay.ps1` |
| `crm.gulya-studio.ru` | туннель → телефон:3000 | публично |
| `dev.gulya-studio.ru` | туннель → телефон:7681 | публично, 401 без пароля |

Почему так: на телефоне коннектор регистрируется и через несколько секунд перестаёт маршрутизироваться (публично 530/1033), при этом обычный HTTPS, TLS/SNI к edge:7844, MTU и скорость в норме. Быстрый туннель ведёт себя так же, смена версии cloudflared не помогает. ПК находится на маршруте, где туннель работает, поэтому он держит коннектор и обращается к телефону по домашней сети.

Пароль консоли хранится на телефоне в `~/pv/.console_cred` (файл с правами 600), в Git и в чат не попадает. Порт 7681 нельзя публиковать напрямую — только через туннель.

### Проверка
```
curl -s -o /dev/null -w "%{http_code}\n" https://crm.gulya-studio.ru/api/health   # 200
curl -s -o /dev/null -w "%{http_code}\n" https://dev.gulya-studio.ru/            # 401
```
На телефоне: `curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:3000/api/health`.
На ПК: `Get-ScheduledTask PV-Relay`, лог `%LOCALAPPDATA%\pv-relay\relay.log`, ошибки коннектора — `%LOCALAPPDATA%\pv-relay\cloudflared.err`.

### Если публичный адрес отдаёт 1033/530
1. Проверить, что ПК включён и задача `PV-Relay` в состоянии Running.
2. Проверить, что телефон в той же сети: `ping 192.168.1.112`, `curl http://192.168.1.112:3000/api/health`.
3. Посмотреть `relay.log`: строка `phone origin reachable=` показывает, виден ли телефон; `public health failed ... restarting connector` — перезапуск коннектора.
4. Если в `%LOCALAPPDATA%\pv-relay\cloudflared.err` все соединения закрылись одновременно (`connection with edge closed`), а `relay.log` показывает восстановление через ~минуту, это перезапуск VPN на ПК. Проверить `Get-Process sing-box | Select-Object StartTime`: время старта совпадёт с обрывом.
5. Если ПК недоступен, публичного доступа не будет: туннель с телефона в этом маршруте не работает.
6. Не запускать второй коннектор того же туннеля одновременно с ПК — edge начнёт балансировать запросы между ними и часть запросов будет падать.

### Автозапуск
- Телефон: `~/.termux/boot/start-pv` (Termux:Boot установлен) вызывает `~/pv/launch-stack.sh`, который поднимает `~/pv/stack.sh` (CRM + ttyd). Отметки — в `~/pv/boot.log` и `~/pv/stack.log`.
- ПК: задача планировщика `PV-Relay` при входе пользователя. Если телефон не отвечает, релей сам запускает стек через ADB (`launch-stack.sh`), повторяя попытки каждые 10 с.
- Фактически после перезагрузки стек поднимает именно релей: прошивка TECNO откладывает boot-receiver Termux:Boot (`PENDING OFFLOAD`, затем заморозка `Hiber`), поэтому полагаться на Termux:Boot нельзя. Проверено: публичный адрес восстанавливается за ~50 с после reboot.
- Следствие: телефон должен быть подключён к ПК по USB (ADB). Если USB отключён и телефон перезагрузился, откройте Termux и выполните `bash ~/pv/launch-stack.sh`.
- `deployment/termux/supervise-pv.sh` — резервный супервизор коннектора для телефона. Оставлен на случай, если маршрут телефона начнёт работать; в текущей схеме не используется.

## Чек-лист первичной установки

Эти пункты описывают установку с нуля; на TECNO AD11 основная часть уже выполнена.

1. После восстановления ADB выполнить `adb devices -l`, подтвердить USB-отладку на разблокированном телефоне. Проверить `node -v`, `node --input-type=module -e "import 'node:sqlite'"`, доступную память, место, питание и температуру. Не отключать температурную защиту.
2. Перед обновлением сделать проверенную резервную копию. Передавать исходники, package-lock.json и проверенный dist; сохранять рабочие `.env`, БД, вложения и конфигурацию туннеля. `npm ci` выполняется на телефоне, node_modules с Windows не копируется.
3. Установить Termux:Boot и termux-services. Создать приватный `.env`: `NODE_ENV=production`, `HOST=0.0.0.0`, `PORT=3000`, `COOKIE_SECURE=true`, случайный SESSION_SECRET не короче 32 символов. `0.0.0.0` нужен, потому что коннектор обращается к CRM по домашней сети; порты 3000 и 7681 должны быть доступны только в доверенной сети. Секреты не добавлять в Git.
4. Выполнить `bash deployment/termux/setup-services.sh`. Проверить `curl --fail http://127.0.0.1:3000/api/health`. Проверить вход администратора через приватное подключение. Не включать публичный туннель, пока первичная настройка доступна без авторизации.
5. Проверить существующий named tunnel и его приватный конфигурационный файл. Ingress должен направлять `crm.gulya-studio.ru` на `http://127.0.0.1:3000`; последняя запись — `http_status:404`. Настроить DNS через подключённый аккаунт Cloudflare. Не печатать токены и tunnel credentials. После проверки отдельно настроить supervised-службу cloudflared.
6. Проверить HTTPS, cookie Secure/HttpOnly, отсутствие публичного доступа к БД и вложениям без входа, вход сотрудника, права и PWA на реальном Android. После перезагрузки и выключения экрана проверить автозапуск служб; wake-lock не заменяет эту проверку.
7. `npm run backup -- create /private/path/snapshot` создаёт новый каталог со снимком SQLite, связанными вложениями и контрольными суммами. `npm run backup -- verify /private/path/snapshot` проверяет копию. `.env` и tunnel credentials хранить отдельно в приватном защищённом месте.
8. `npm run backup -- restore /private/path/snapshot /private/path/restore-test` восстанавливает в НОВЫЙ каталог, не заменяя рабочую БД. Для проверки запустить отдельную копию сервера с DB_PATH и UPLOAD_DIR из этого каталога. Проверить вход, финансы, склад и открытие файлов. Перед переключением рабочей БД остановить CRM; сохранить текущие данные.
9. Ежедневный запуск резервного копирования и перенос на приватный внешний сервер требуют настройки расписания, адреса и аутентификации назначения. Эти подключения здесь не настроены. Не публиковать резервные копии через каталог dist или публичный web-сервер.
10. Перед публикацией выполнить `npm test`, `npm run lint`, `npm run build`, `npm run test:browser`. После установки запустить `npm run test:load` с PV_BASE_URL, PV_LOGIN, PV_PASSWORD, PV_WORKERS=15, затем 30. Сохранить отчёт p95, ошибки и отдельно измерить температуру/память телефона. Один общий тестовый аккаунт и только чтение не воспроизводят все действия 30 сотрудников; результат не является гарантией ёмкости.

## Офлайн-сценарии

Проверить пять сценариев из плана: материалы без повторного списания; две правки одной записи с конфликтом; файл после перезапуска браузера; запись, удалённая администратором; выход/смена аккаунта с оставшимися операциями. Очередь: максимум 100 операций и 40 МБ, одна операция до 13 МБ; серверная загрузка одного файла до 12 МБ. Операции старше 30 дней отклоняются и требуют проверки пользователем. В конфликте нужно обновить данные, удалить старую операцию из очереди и повторно внести нужную правку. Удаление из очереди не отменяет действие, которое сервер уже мог выполнить при потерянном ответе; сначала проверить актуальные данные.
