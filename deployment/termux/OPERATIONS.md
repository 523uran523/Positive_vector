# Termux: запуск и проверка

Эти файлы подготовлены; установка на TECNO AD11 в текущей сессии не выполнена.

1. После восстановления ADB выполнить `adb devices -l`, подтвердить USB-отладку на разблокированном телефоне. Проверить `node -v`, `node --input-type=module -e "import 'node:sqlite'"`, доступную память, место, питание и температуру. Не отключать температурную защиту.
2. Перед обновлением сделать проверенную резервную копию. Передавать исходники, package-lock.json и проверенный dist; сохранять рабочие `.env`, БД, вложения и конфигурацию туннеля. `npm ci` выполняется на телефоне, node_modules с Windows не копируется.
3. Установить Termux:Boot и termux-services. Создать приватный `.env`: `NODE_ENV=production`, `HOST=127.0.0.1`, `PORT=3000`, `COOKIE_SECURE=true`, случайный SESSION_SECRET не короче 32 символов. Секреты не добавлять в Git.
4. Выполнить `bash deployment/termux/setup-services.sh`. Проверить `curl --fail http://127.0.0.1:3000/api/health`. Проверить вход администратора через приватное подключение. Не включать публичный туннель, пока первичная настройка доступна без авторизации.
5. Проверить существующий named tunnel и его приватный конфигурационный файл. Ingress должен направлять `crm.gulya-studio.ru` на `http://127.0.0.1:3000`; последняя запись — `http_status:404`. Настроить DNS через подключённый аккаунт Cloudflare. Не печатать токены и tunnel credentials. После проверки отдельно настроить supervised-службу cloudflared.
6. Проверить HTTPS, cookie Secure/HttpOnly, отсутствие публичного доступа к БД и вложениям без входа, вход сотрудника, права и PWA на реальном Android. После перезагрузки и выключения экрана проверить автозапуск служб; wake-lock не заменяет эту проверку.
7. `npm run backup -- create /private/path/snapshot` создаёт новый каталог со снимком SQLite, связанными вложениями и контрольными суммами. `npm run backup -- verify /private/path/snapshot` проверяет копию. `.env` и tunnel credentials хранить отдельно в приватном защищённом месте.
8. `npm run backup -- restore /private/path/snapshot /private/path/restore-test` восстанавливает в НОВЫЙ каталог, не заменяя рабочую БД. Для проверки запустить отдельную копию сервера с DB_PATH и UPLOAD_DIR из этого каталога. Проверить вход, финансы, склад и открытие файлов. Перед переключением рабочей БД остановить CRM; сохранить текущие данные.
9. Ежедневный запуск резервного копирования и перенос на приватный внешний сервер требуют настройки расписания, адреса и аутентификации назначения. Эти подключения здесь не настроены. Не публиковать резервные копии через каталог dist или публичный web-сервер.
10. Перед публикацией выполнить `npm test`, `npm run lint`, `npm run build`, `npm run test:browser`. После установки запустить `npm run test:load` с PV_BASE_URL, PV_LOGIN, PV_PASSWORD, PV_WORKERS=15, затем 30. Сохранить отчёт p95, ошибки и отдельно измерить температуру/память телефона. Один общий тестовый аккаунт и только чтение не воспроизводят все действия 30 сотрудников; результат не является гарантией ёмкости.

## Офлайн-сценарии

Проверить пять сценариев из плана: материалы без повторного списания; две правки одной записи с конфликтом; файл после перезапуска браузера; запись, удалённая администратором; выход/смена аккаунта с оставшимися операциями. Очередь: максимум 100 операций и 40 МБ, одна операция до 13 МБ; серверная загрузка одного файла до 12 МБ. Операции старше 30 дней отклоняются и требуют проверки пользователем. В конфликте нужно обновить данные, удалить старую операцию из очереди и повторно внести нужную правку. Удаление из очереди не отменяет действие, которое сервер уже мог выполнить при потерянном ответе; сначала проверить актуальные данные.
